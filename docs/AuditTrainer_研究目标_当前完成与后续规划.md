# AuditTrainer：研究目标、阶段进展与后续规划

> 本文概括 AuditTrainer 的研究问题、当前已经完成的工程与实验工作，以及下一阶段基于 APPS 和 TACO 扩大责任分解与履约执行样本的计划。文中“完成”指相应实现、数据检查或实验已经有可复核产物；它不等同于已经证明了跨任务、跨数据集的最终科学结论。

## 一、研究目标

AuditTrainer 研究的是一个比“生成一段能通过测试的代码”更严格的问题：模型能否先把任务拆成可审计的责任单元，再让每个单元在明确契约下完成实现、交接和组合，最后用受控实验判断成功来自哪一个因素。

### 1. 细粒度责任分解

责任分解的目标是把一个根任务表示为一组有边界的函数或模块职责，并明确每个节点的输入、输出、拥有的义务、允许使用的依赖和下游交接方式。分解结果不是若干互相独立的代码片段，而是一棵可以注册、执行、验证和追踪的责任图。

AuditTrainer 当前采用函数/模块粒度和显式契约作为主要学习载体。每个计划节点至少需要回答以下问题：

- 哪个节点拥有这项义务，父节点是否仍保留自己的聚合或组合责任；
- 子节点的输入和输出是什么，接口是否与父节点的契约一致；
- 父节点是否实际消费了子节点的当前版本、哈希和证据；
- 分解是否遗漏必要步骤、重复同一责任，或把一个完整责任拆成无法独立验证的片段。

因此，`SPLIT` 的出现本身不算成功。只有当分解边界与责任语义、接口和后续执行相互一致时，它才是可用于训练和因果比较的有效样本。`ATOMIC` 也不是简单的负例：当进一步拆分没有可测收益，或执行成本超过收益时，停止细分可能是正确决策。

### 2. 责任约束下的履约执行

责任分解必须在执行阶段兑现。模型需要在节点契约约束下编写代码，遵守依赖边界，完成局部验证，并在父节点中以明确动作消费子节点结果。宿主只提供固定的执行控制、输入输出包装和验证证据，不替模型补写算法、自动添加调用或替它完成责任交接。

AuditTrainer 将履约拆成可独立审计的状态：

1. 计划是否被正确注册，节点契约和责任边界是否完整；
2. 节点代码是否通过编译、接口和隔离执行检查；
3. 局部可见测试和离线私有测试是否通过；
4. 父节点是否消费正确的子节点版本，并实际使用返回值；
5. 最终根程序是否同时满足功能、契约、消费和协议要求。

系统保留 `PASS`、`FAIL`、`UNKNOWN`、协议拒绝和基础设施错误等不同结果。功能通过但责任越界、遗漏消费或使用过期版本的程序，不能被当作责任履约正例。有限修复也必须绑定到冻结的契约、源码版本、责任边界和可见证据中，并保留回滚和重放记录。

### 3. 因果分析

责任分解、执行器能力、门控选择、输入摘要、重试和评分实现都可能改变最终成功率。如果只比较最终通过数，就无法知道收益究竟来自更好的分解、执行器补偿、提示格式、更多重试，还是评分漏洞。因此，AuditTrainer 把因果分析作为第三条主线，而不是在实验结束后对结果做事后解释。

核心方法是固定其余条件，只改变一个因素，并保存完整的中间状态和反事实证据。典型对照包括：

- 同一任务、同一父状态下比较 `ATOMIC` 与合法 `SPLIT`；
- 同一责任计划下替换执行器，观察局部履约和根成功的变化；
- 冻结正文、执行器和根门控，只校准内部或根门控；
- 保持源码和测试不变，只增加或移除父职责摘要、消费证据或版本绑定；
- 对已知失败程序做单点人工修正，判断失败是否由某一责任边界导致，再与模型自主修复分开计分。

只有在任务、种子、预算、输入、测试、模型冻结和评分边界都可比时，配对胜负才可作为局部因果证据。单个开发任务上的正收益用于决定下一步实验，不直接外推为普遍能力。

三条主线的关系可以概括为：

```text
任务与契约
    ↓
责任分解（ATOMIC / SPLIT 与节点边界）
    ↓
契约化履约（实现、验证、消费、组合与有界修复）
    ↓
证据聚合（功能、责任、协议、成本与版本状态）
    ↓
受控因果比较（冻结因素、单变量干预、配对评测）
```

## 二、目前已经完成的工作

### 1. 可执行的责任审计框架已经建立

F1–F9 完成了从动作协议、递归运行时、沙箱执行、契约和验证器，到轨迹记录、证据指纹、有限修复和统一评测接口的基础实现。框架能够保存每次计划、实现、验证、消费、拒绝、重试和修复的完整过程，而不是只保存最后一份代码。

主要能力包括：

- 显式的 `ATOMIC` / `SPLIT` 计划和逐节点契约；
- 深度优先递归调度、共享预算、版本化源码和依赖闭包；
- 隔离执行、可见 suite、离线私有检查以及基础设施错误隔离；
- 对 `selected`、`linked`、`called`、实际消费和证据有效性的区分；
- 受责任边界限制的定位、ticket、候选修复、回滚和重放；
- 面向 APPS 的输入适配、导入和评测入口，以及面向 TACO 的下载、转换和训练脚本。

主机制在 A3 阶段冻结为逐节点层次契约、函数/模块所有权、显式消费、责任筛选和冻结补集修复，配置见 [`configs/frozen_mechanism.yaml`](../configs/frozen_mechanism.yaml)，数据检查协议见 [`docs/data_check_protocol_v1.md`](data_check_protocol_v1.md)。

### 2. 数据构造和责任监督流程已经跑通

A4 完成了 TRAIN pilot 的数据构造流程：新建 50 个 TRAIN root、覆盖 10 个任务族，在同一父状态下执行多种合法计划，审查策略事件并导出 2,240 条 TRAIN 动作。数据导出区分责任支持、协议监督、功能对照和 `UNKNOWN`，没有把宿主事件或单纯功能通过自动标成责任正例。

A5 和 A6 完成了四组责任/功能监督对照，以及一次受控的父职责重分配修订。F00、F10、F01、F11 和 F11_C 均完成了实际 QLoRA 训练、磁盘重载、冻结检查和后续执行评测。结果证明了责任监督和履约监督可以被实际训练与评测，但局部收益、格式稳定性和父组合能力仍受任务结构与执行器能力影响，不能据此宣称模型已经获得普遍的细粒度分解能力。

### 3. 规划器、执行器和门控的因果诊断已经形成连续证据链

A2 对粗粒度、函数级、层次契约和多种责任定位方式进行了完整的开发比较；A3 冻结了主机制；PR0、PR1 和 PR1C 完成了规划表示适配、共同格式 SFT、有限根规划 RL 以及多轮采样对照；随后 B3 系列继续比较固定计划、父摘要、回报估计、模式权重、任务覆盖和泛化。

这些工作已经回答了几个工程上关键的问题：

- 合法分解可以被注册、执行、验证和恢复，失败原因可以定位到责任、接口、消费、协议或功能层；
- 某些固定任务和父聚合状态存在可测的分解收益，但收益并不在所有任务上重复出现；
- 冻结摘要、父职责边界、根/内部门控和执行器训练都可能改变结果，必须通过配对和冻结条件分开研究；
- 现有小规模 RL 对照尚未证明大规模 RL 是必要条件，也尚未证明自然分解能力已经跨任务泛化。

当前执行器线的最新 pilot 在新输入根上将成功数从 **2/8 提升到 6/8**，但保持集从 **16/16 降到 13/16**，因此保持修复 pilot 已完成设计和启动核对，尚未把该候选替换为通用默认。完整阶段状态和边界见 [`STATUS.md`](../STATUS.md) 及 [`reports/`](../reports/) 中的分阶段报告。

### 4. 当前尚未完成的部分

目前尚未完成的是大规模、跨任务族的责任分解与履约执行数据生产，也没有完成 APPS/TACO 上的统一样本质量筛选和正式训练。A7 及其后的大规模样本工程仍是下一阶段工作。现有结果主要来自固定开发族、TRAIN 状态和受控配对，不能替代独立任务族、未见接口和跨数据集验证。

## 三、后续规划：基于 APPS 和 TACO 扩大样本生产

下一阶段将把 AuditTrainer 从“验证框架和小规模实验平台”推进为“责任分解—履约执行样本生产线”。总体目标不是把所有任务强行拆分，而是用当前框架大量产生候选责任图和执行轨迹，再筛选出能够支持不同训练目标的高质量样本。

### 阶段 0：固定来源、任务协议和数据边界

1. 固定 APPS 和 TACO 的数据集 revision、下载清单、文件哈希和许可证说明；原始大数据集不直接提交仓库。
2. 将题目统一成 AuditTrainer 的任务、契约、可见输入、离线私有检查和参考解格式。
3. 按任务族、接口形态、输入输出类型、难度、递归深度和潜在责任结构建立分层清单。
4. 预先划分 TRAIN、DEV 和 VALIDATION，防止同题变体、同一参考解或同一责任模板跨分区泄漏。

### 阶段 1：责任分解候选的大规模采集

对每个 APPS/TACO 任务，在固定父状态和预算下采集多类候选：

- `ATOMIC`：由单节点承担完整实现，作为功能和成本基线；
- 一层 `SPLIT`：将准备、计算、聚合、验证或接口转换等责任分开；
- 多种合法责任排列：交换子节点边界、父聚合位置和消费路径；
- 模型自然计划、拒绝后重试和有界修复计划，全部保留而不只保留成功样本。

每次采集记录模型输入、动作序列、计划版本、责任图、源码、随机种子、预算、重试、token 成本和最终状态。候选生成阶段不能看到离线私有答案，也不能用最终成功与否反向修改当时的 observation。

### 阶段 2：责任约束下的履约执行

每个候选责任图都经过当前固定执行器和沙箱：

1. 注册每个节点的输入、输出、契约义务和允许依赖；
2. 运行局部可见检查，确认节点接口和局部语义；
3. 运行离线私有检查，确认根程序的真实功能；
4. 检查父节点是否消费正确版本、哈希和证据，并实际使用返回值；
5. 记录根级功能、责任、协议、基础设施和成本状态；
6. 对允许的失败执行有界修复，保留原版本、修复版本和因果标签。

采集结果至少要能区分以下情况：

| 类别 | 含义 | 用途 |
| --- | --- | --- |
| 功能通过且责任通过 | 根功能正确，责任边界、消费和契约均满足 | 高质量正例 |
| 功能通过但责任违规 | 结果正确，但越权、漏消费或契约不完整 | 责任硬负例 |
| 责任正确但功能失败 | 计划和交接正确，算法或实现失败 | 执行履约诊断 |
| 协议拒绝或证据过期 | 版本、哈希、JSON、消费或动作协议不满足 | 协议负例 |
| 基础设施错误 | 沙箱、GPU、进程或评分设施异常 | 过滤，不作为模型标签 |

### 阶段 3：构造可解释的因果对照

样本生产不能只追求数量。对有潜在价值的任务，优先构造同状态、同种子、同预算的配对或多臂样本：

- `ATOMIC` 与已注册、责任不同的 `SPLIT` 配对；
- 相同责任图下，不同执行器或执行器版本配对；
- 相同正文下，门控选择 `ATOMIC`、`SPLIT` 和自然计划的配对；
- 固定子组件，只改变父聚合或消费动作；
- 固定模型和计划，只改变摘要、接口说明或一项责任义务；
- 对同一失败程序做单点人工修正，再与模型自主履约结果分开保存。

只有在配对输入、任务状态、测试集合、预算和冻结组件一致时，才把结果差异作为候选因果信号。若两臂都失败、差异只出现一次，或伴随评分/基础设施异常，则保留为诊断记录，不强行转成正负回报。

### 阶段 4：样本筛选与训练集构建

样本筛选分为硬门槛、质量分层和任务平衡三步。

**硬门槛**：

- 来源 revision、任务哈希、参考解和测试边界完整；
- 没有基础设施错误、私有信息泄漏或未来状态进入 observation；
- 计划、源码、依赖、消费、版本和证据可以重放；
- 局部和根级检查的可见/私有范围明确；
- 同一任务或同一参考程序的重复轨迹已经去重并绑定到同一数据分区。

**质量分层**：

- **A 级正例**：责任分解完整，契约履约、子节点消费和根功能均通过，且在重复种子或配对中稳定；
- **B 级正例**：责任和局部履约通过，但根级功能仍有可解释算法错误，用于执行器诊断或修复训练；
- **责任硬负例**：功能通过但责任边界、契约、消费或版本约束明确违规；
- **功能对照**：责任计划正确但实现失败，用于区分规划能力和履约能力；
- **协议负例**：动作格式、证据、版本或交接不合法，但不与基础设施错误混合。

**平衡与拆分**：

- 按 APPS/TACO、任务族、输入输出接口、责任深度、节点数和 `ATOMIC/SPLIT` 比例分层；
- 控制 token 成本和代码长度，避免训练集只学习“短代码更容易成功”；
- 保留足够的困难负例和近成功样本，不把所有失败样本简单丢弃；
- 以任务族和责任模板为单位划分 VALIDATION，检查未见题目、未见接口和跨数据集迁移；
- 训练集中的正例、负例和因果配对分别维护 manifest，后续训练不直接读取未经审核的原始轨迹。

### 阶段 5：分阶段训练，而不是一次性扩大 RL

建议按“先履约、再分解、后选择”的顺序推进：

1. **执行器履约 SFT**：先用高质量契约、实现、验证和消费轨迹，训练模型在责任边界内稳定完成节点任务；
2. **规划器/分解 SFT**：使用通过质量门槛的责任图、计划动作和困难负例，学习何时拆分、如何分配父子职责；
3. **门控和价值估计**：只使用同状态配对中回报差异稳定、评分边界清楚的样本，学习选择 `ATOMIC` 或 `SPLIT`；
4. **有限 RL 或其他偏好优化**：在执行器和评分协议稳定后，针对有重复收益证据的任务族做小规模单变量对照；
5. **冻结模型的因果复验**：所有训练候选都必须在独立任务族、不同种子和未见接口上复验，不能用训练筛选结果替代泛化评测。

### 阶段 6：最终评测指标

后续评测同时报告能力、责任、因果和成本四类指标：

- **分解质量**：责任覆盖率、重复/遗漏率、契约完整率、计划注册率、首次 `SPLIT` 选择率；
- **履约质量**：局部可见/私有通过率、根级通过率、有效消费率、版本/哈希一致率、协议拒绝率和有界修复成功率；
- **因果证据**：配对胜负、每任务族效果、不同执行器和门控条件的单变量差异，以及结果稳定性；
- **泛化与成本**：APPS/TACO 未见任务族、未见接口和跨数据集迁移表现，模型调用次数、输入输出 token、运行时间和分解额外成本。

## 四、阶段性判断标准

后续工作遵循三个停止条件：

1. 如果大量任务没有稳定的分解收益，就不把 `SPLIT` 作为统一最优标签，保留 `ATOMIC` 与条件分解并行学习；
2. 如果分解收益存在但执行器无法履约，优先修复契约、接口和消费训练，不扩大规划器 RL；
3. 只有当责任分解、履约执行和回报差异在独立任务族上同时稳定，才扩大门控或 RL 预算，并把结论推广到更大范围。

AuditTrainer 当前已经完成了可执行、可审计、可做单变量干预的责任分解与履约框架，并通过多轮 pilot 识别了分解收益、执行缺口和评分边界。下一阶段的核心不是继续堆叠小规模对照，而是利用 APPS 和 TACO 大量采集结构化轨迹，经过严格筛选形成可分别训练规划器、执行器和门控的数据集，最终用独立任务族的因果配对和成本分析判断细粒度责任分解何时真正带来可重复的履约收益。
